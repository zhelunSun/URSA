# 第一章“验证”层级表

> 中文写作中“验证”容易同时指规则检查、软件测试、历史轻量评测和正式实验。本表固定它们的对象、证据与允许措辞。

最短区分是：第一章检查“能否正确运行并留下证据”，第二章判断“方法和结论是否有科学依据”，
第三章评价“完整系统在真实任务中是否可靠、有用”。第一章不能因为有了规则检查，就声称已经
完成第二章的科学约束或第三章的独立系统评测。

| 层级 | 验证对象 | 当前例子 | 能证明什么 | 不能证明什么 |
| --- | --- | --- | --- | --- |
| V0 运行前规则检查 | 单个工具、数据、参数或步骤连接是否满足声明约束 | 文件、类型、顺序、必需波段/配置、输出约定；grid/CRS/nodata 底线检查 | 某个候选步骤是否违反当前明确规则 | 方法总体有效或结果科学正确 |
| V1 软件测试 | 实现是否符合代码级预期 | 工作流/ReAct 单元测试、18 个工具注册检查 | 回归稳定、接口与有限不变量 | 真实模型行为、跨任务有效性 |
| V2 诊断小样 | 机制在一个小样上是否产生可检查行为 | 修补记录、Sentinel-2 LST 受控停止、语义波段真实工具运行 | 链路贯通、事件记录、失败定位与已编码底线条件 | 因果提升、跨任务泛化、主题精度 |
| V3 历史系统评测 | 已发表系统相对历史基线的初步表现 | 20 条请求：10 条单步 + 10 条多步；规划/结果正确率与 token | 原 ExpertsRS 可行性与初步比较 | 本轮新增机制的效果 |
| V4 第一章机制实验 | 三个研究对象在同任务条件下的增量 | B0 原始对话、B1 静态预先规划、B2 反馈后调整计划/图、B3 检查点局部恢复 | 计划完成、错误定位、恢复范围与成本的因果信号 | 更广用户效用、遥感知识质量或主题精度 |
| V5 系统与用户评测 | 真实任务中结果、轨迹、恢复和用户效用 | 第三章任务—轨迹—结果—评价 | 系统可靠性与用户价值 | 不替代第一章机制对照 |

## 检查能力不等于审核 Agent

第一章把检查分为三类责任：运行时用固定规则检查工具约定、权限、预算、产出完整性和停止
状态；Scientist/Engineer 根据真实反馈对方法与实现负责；运行外独立评测在标准答案隔离下评价
过程和最终结果。规则无法判断的语义问题才可触发无执行权限的临时审核器，其输出只是带依据的
建议，不是自动批准。

因此，增加审核步骤不要求增加常驻 Agent。若未来比较“无审核器 / 按需审核器 / 常驻审核器”，
它属于实验条件，必须单独报告效果、相关错误、成本与延迟。

## 原 20-request benchmark 的正确角色

它承担三项功能：

1. 证明研究问题不是凭空出现：多步任务在原系统中仍存在明显 planning/result gap；
2. 提供历史 baseline 与典型任务来源；
3. 为新实验设计 task family、failure family 和评分标准提供 lineage。

它不应直接承担：

- 新增 typed workflow/validator/repair 的效果证明；
- 与当前模型、工具和预算不匹配的数值复用；
- 从旧 20 条中边看 gold 边修改方法后再报告无隔离结果。

2026-08-09 的架构澄清进一步规定：第一章若复用这 20 条，只标注角色交接、计划/动作一致性、观测后修订、终止状态、工件闭合和 trace 完整性。`scientific_risk_level`、指数阈值是否构成有效遥感代理、知识证据充分性等 rich gold 不再作为第一章主指标；它们可以保留为第二章候选材料，但不能反向塑造第一章 runtime 方法。

## 原始资产恢复门禁

当前 URSA 和 `research-harness` 只保存摘要，没有找到 20 条逐项请求或评分记录。恢复时至少需要：

- 20 条原始 user requests 与 single/multi-step 标签；
- 当时的 expected workflow/result 或专家评分表；
- ExpertsRS、base LLM、single-agent 的逐项结果；
- model/config/prompt、token 统计和失败说明；
- 两个 case 与 benchmark 是否共享任务或数据；
- 哪些材料已公开、哪些只能用于论文内部。

资产进入本系统后先标为 `historical-source`，再决定是只做 provenance、补充复现，还是映射到新的独立 task set。

## 第一章最小匹配实验

第一章不需要把 20 条全部重做成复杂 gold 才能验证方法。先选择少量能够出现“首步计划不足—真实观测—局部修订—恢复/停止”的任务，在相同模型、工具、上下文、预算和输出要求下比较：

1. `B0`：原始对话式协作；
2. `B1`：现有静态 `TaskSpec/WorkflowGraph/validator` 路径；
3. `B2`：可修改的计划与随执行更新的过程图；
4. `B3`：在 B2 上启用逻辑 checkpoint 局部恢复。

主指标保持简单：任务是否闭合、观测后错误修订是否正确、失败后重做范围、错误成功率、trace/graph 完整性；token、tool call、wall time 和人工澄清次数作为成本指标。这个实验回答第一章的运行机制问题，不评价 NDVI 阈值是否具有跨场景科学效度，也不替代后续章节的独立结果评测。

## D2 能把第一章闭合到什么程度

D2 已于 2026-08-11 形成“第一章升级后的最小方法原型闭环”：三个研究对象在无 API、真实
工具故障小样中贯通，43 项相关测试通过，计划修改、过程图、失败恢复和权限拦截都有可读证据。
这足以冻结架构、完成方法章节初稿和 M1 工程证据包。

D2 仍不足以声称“方法提高了真实模型可靠性”。为了让第一章具有最小科学效果证据，在最终
定稿前还需要一个刻意压缩的 D3-light：选择少量代表任务，在相同模型、工具和预算下比较静态
预先规划、反馈后调整计划、增加检查点恢复三种条件。建议先用 4--6 个任务试跑，任务和评分
稳定后才决定是否扩展；不在第一章做完整用户研究、主题精度评估或科学知识消融。

2026-08-11 已从冻结的 20 条中选择 5 条 D3-light 候选任务：ID 2（正常完成）、3（缺少注册
工具）、10（真实数据前置条件停止）、11（多步故障恢复）和 13（Manager 澄清）。原始请求不
改写；只有 ID 11 在 NDVI 成功后注入一次不改变科学语义的 threshold 临时写入失败。外部评分
合同与 Agent 可见输入通过 loader 分离，并有无泄漏测试。当前只完成数据和评分设计，API gate
仍关闭。

一次 `5 tasks × 3 conditions = 15 runs` 只能形成 live integration smoke；若配置稳定并需要最小
效果信号，再固定三个独立重复得到 45 runs。两者都不能支持广泛统计优越性，是否增加重复必须
在看到首轮成本和失败模式后决定。

截至 2026-08-12，15 个槽位已由同一 runner、确定性替身决策器和外部 evaluator 完成 no-API
dry run；它确认计划/权限/工具反馈/停止/恢复/过程图与评分合同能一起工作，但不能替代真实模型
证据。live provider 尚未实现，API 双门禁仍关闭；这一状态比“准备调用 API”更准确。

因此第一章验证只保留三包：

1. **软件正确性**：既有回归测试 + D2 新增单元测试；
2. **机制可运行性**：D2 的计划修改、局部恢复、权限拦截三个无 API 小样；
3. **最小效果信号**：D3-light 的少量同任务真实模型对照。

第二章单独评测科学约束是否正确改变行动；第三章再承担完整结果、过程、故障、用户和外部
效度评测。这样不会把第一章的验证无限拉长。

## 推荐论文措辞

> 已发表研究通过 20 条请求的轻量验证集提供了系统可行性和多步规划不足的经验依据。本章在此基础上改变验证对象：不再只评价对话终点或整体计划是否正确，而是将任务、operator、artifact 和 dependency 显式化，检验 violation detection、appropriate repair/stop、subgraph edit 和 trace completeness，并通过匹配条件区分各机制的增量。
