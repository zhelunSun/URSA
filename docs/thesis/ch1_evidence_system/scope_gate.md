# 第一章范围与准入门槛

> 目的：让系统现代化，但不让工程能力、科学问题和章节叙事失控。

## 唯一核心科学问题

> 面向非遥感专业用户提出的开放式城市森林分析需求，如何构建能够保持用户意图、组织专业
> 数据与工具，并依据运行反馈可靠完成任务的多智能体遥感工作流？

本章把工作流可靠性操作化为需求保持性、执行有效性、反馈适应性和结果可核验性。可调整规划、
过程图和检查点局部恢复是方法机制，不取代上述领域问题。

新工作若不能直接支撑这个问题、其必要实现接口或其正式证据，默认不进入当前第一章主线。

## 冻结的一句话主线

> User-centric RS 是领域出发点；第一章进一步研究开放需求驱动的多智能体遥感工作流如何可靠
> 形成和运行，并以需求、执行、反馈与结果证据四个维度接受检查。

已发表 ExpertsRS 的“自然语言需求 → Manager → Scientist → Engineer/Executor → 可视化结果”
是思想母体，不因运行时升级而废弃。新增研究对象不是自然语言交互、角色数量、ReAct 或
工作流图本身，而是让系统根据真实工具反馈调整计划、保存过程并从局部失败继续执行。

## 三个研究对象

1. **可调整的分层规划**：Manager 固定用户意图边界；Scientist 维护总体和当前阶段的方法计划；
   Engineer 生成下一工具动作。计划是面向未来的暂定假设，不要求执行前形成完整静态图。
2. **随执行更新的过程图**：逐步记录原计划、实际动作、工具反馈、产出、失败和改道关系。
   它把规划和真实执行连接起来，供检查、解释和继续思考，但不代替规划，也不是预写剧本。
3. **基于检查点的局部恢复**：失败后保留此前已经验证的有效产出，只修改受影响的部分并
   尝试替代路径；不承诺撤销已经发生的外部不可逆操作，也不称为学习或自我进化。

### 规划、执行与过程图的关系

1. 规划说明系统接下来准备怎样做；执行说明系统实际上做了什么、看到了什么、产生了什么。
2. 工具反馈可以触发计划修改，但旧计划、失败动作和修改原因都必须保留，不能用最后一次成功
   覆盖此前发生的事实。
3. 过程图由上述事实逐步整理出来。它可以帮助人和 Agent 检查、解释和继续思考，但不要求
   Agent 在执行前先服从一张完整固定的图。
4. 失败后从检查点形成替代路径，复用已经验证的产出，并明确记录原路径为何停止、新路径如何
   继续。
5. Agent 日常只读取与当前决策有关的简要信息，不把全部运行记录机械塞入上下文。

### 为什么分层规划不是搜索树

| 对象 | 主要问题 | 当前最小形式 | 是否确定 |
| --- | --- | --- | --- |
| 分层规划 | 接下来准备怎样做？ | 总体目标、当前阶段、下一动作 | 不是；Scientist 可按反馈修改 |
| 过程图 | 实际发生了什么、为何改道？ | 计划版本、动作、反馈、产出、失败和路径关系 | 给定运行记录后应能确定性重建 |
| 检查点 | 失败后从哪里安全继续？ | 最近一次完成工具调用、通过检查且产出有效的状态 | 保存内容确定；后续选择可调整 |

树搜索是在同一时刻展开和评价多个未来候选，分层规划则是把同一条当前计划按尺度拆开。两者
可以结合，但并不等价。D2 只在真实反馈触发失败时形成一条替代路径，不主动展开搜索树，也不
引入 MCTS/LATS 的采样、价值估计或回传。

D2 会记录每一步执行轨迹，但不把每条消息都当成可恢复检查点。检查点只建立在安全边界：工具
动作已经结束、执行后检查通过、有效产出已经登记。它保存当前计划版本、继续位置和有效产出
引用，不复制大型栅格，也不负责撤销外部不可逆操作。

## 三层准入

| 层级 | 可以进入的内容 | 判定标准 |
| --- | --- | --- |
| 方法核心 | 可调整的分层规划、随执行更新的过程图、基于检查点的局部恢复 | 能形成清晰操作定义、对照条件和失败边界 |
| 运行支撑 | 最小任务说明、工具和产出约定、ReAct、状态、预算、过程记录、规则检查、权限检查和唯一执行入口 | 连接 Brain、Tools 与 Data；必要但不逐项单列创新 |
| 评测 | 历史 20 条任务、故障小样、同任务对照、指标和错误分析 | 能区分既往可行性、诊断证据和正式效果证据 |

任何新功能只能有一个主要层级。若同时声称属于多个层级，先拆分任务和 claim。

4. **D3：真实模型集成 pilot——已于 v0.5.3 完成**。冻结 5 个任务 × 3 个条件，在统一 runtime

## 检查责任与权限边界

检查是贯穿系统的责任，不默认增加常驻“审核 Agent”：

- Manager 负责用户意图、替代方案和高风险动作的确认；
- Scientist 负责方法计划是否合理，并根据规则检查和真实工具反馈修改计划；
- Engineer 负责工具可行性、参数和产出是否闭合；Executor 不自行改变方法，只执行已授权动作；
- 运行时在执行前、执行中和执行后检查工具约定、权限、预算、产出完整性和停止条件，并把
  结果加入过程记录；
- 独立评测位于系统外部，只评价过程和最终结果，不能参与同一次运行并向系统泄露标准答案。

只有在语义问题无法由固定规则、领域工具或用户确认解决，并且有明确触发条件时，才允许临时
调用只读审核器。它没有工具执行权，也不是第四个常驻角色；其意见必须附依据和不确定性，
最后仍由原角色或 Manager 决定修改、询问用户或停止。

D1 只冻结一个最小原则：系统在真正执行动作前，应能记录“谁、对什么资源、准备做什么、是否
允许、限制是什么、为何这样决定”。当前仍由 Executor 作为唯一执行入口；完整企业身份系统、
密钥管理、多租户、容器隔离和外部协议授权均不在 D1 实现。具体字段只属于技术附录，不需要
研究者逐项审批。

## 生产控制面的分期

前述生产方向不形成五条并行开发线：

1. **D1 只做接口盘点**：记录检查责任、权限检查、过程追踪和遥感产出标准的未来对应关系，
   不接云服务；
2. **D2/D3 只实现研究必需的最小量**：稳定标识一次运行、计划、事件和产出，执行前检查
   权限，记录模型/工具/数据版本、逻辑检查点以及过程/结果/成本指标；
3. **章节完成后的工程待办**：遥测导出、遥感服务标准、容器隔离、持久化队列和状态、企业
   权限、在线监控与跨系统 Agent 通信。

后一层只有在部署、求职演示或创业产品出现明确需求时才启动，不反向扩大第一章创新点。

## D2 的人工原则与工程验收分离

D2 的以下三条原则已于 2026-08-10 获研究者认可；首轮不需要真实模型：

1. 真实发生过的动作、结果和失败按时间保留，不能被最后一次成功覆盖；
2. 过程图由这些事实自动整理出来，用于检查和继续思考，而不是预先写死流程；
3. 先用无 API 小样验证“反馈后改计划、失败后换路、越权被拦截”，再讨论真实模型效果。

研究者只需要决定这三条。下面是执行者负责的工程验收清单，不是新的论文概念，也不要求研究者
审批类名或字段：

1. 同一次运行里能看到修改前后的计划、触发修改的真实工具反馈以及父子关系；
2. 每条运行记录有稳定编号、先后顺序、责任角色和相关对象，失败事实不会被覆盖；
3. 仅根据运行记录可以重新得到同一张简要过程图，且不绑定 AutoGen 或 LangGraph；
4. 一个注入故障能形成检查点和替代路径，并明确复用了哪些已验证产出；
5. 一个越权或越界写入在 Executor 执行前被拒绝或要求确认，并留下可读原因；
6. 执行前、执行后和结束时的固定规则检查都有可读记录，默认路径不增加审核 Agent；
7. 旧工作流、ReAct 和科学前置条件测试保持通过；新测试覆盖计划修改、过程图重建、权限、
   路径关系和未受影响产出的复用；
8. 不实现任意回滚、云服务、图数据库、完整企业权限、遥感服务或持久化分布式运行时。

D2 只证明对象能贯通和失败路径可检查；真实模型效果仍属于 D3。

## 新任务准入问题

开始代码前必须能回答：

1. 它解决的是哪个已经观察到的失败，而不是追随哪种流行技术？
2. 它主要属于方法、运行支撑还是评测？
3. 它对应哪条可追溯结论；会改变当前允许的论文措辞吗？
4. 最小反例和停止条件是什么？
5. 如果失败，会留下什么可复用证据？
6. 是否会让第一章侵入第二章科学约束或第三章用户评测？

无法回答时，先写六格升级卡，不写实现。

## 每个会话的结束检查

- snapshot 是否刷新；
- source 是否 tracked/reconstructable；
- test 与 scientific evidence 是否分开；
- claim registry 是否需要升级或降级；
- 是否新增了不属于最小队列的功能；
- 下一动作是否仍只有一个。
