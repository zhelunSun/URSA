## 30 秒面试版

我研究怎样让非遥感专家提出的需求形成可执行、可检查的工作流。URSA 把模型计划与实际工具执行分开，运行时检查依赖、权限和产物，并保留失败和过程证据。已有真实 NDVI 任务与运行内局部恢复；北京分类工具链已接入同一运行时，但真实开发验证仍暴露多余澄清和协议失败。我目前重点补齐领域决策稳定性；知识驱动求解、生产级恢复和方法效果分别验证。


## 论文核心思想连续性版

原论文的 `Data–Tools–Brain` 没有被新运行时替代：Data 提供输入和真实工具反馈，Tools 从自由代码生成升级为受控工具，Brain 保留 Manager 澄清、Scientist 方法规划、Engineer 实现的自主分工。运行时只是三者共用的状态、执行边界和证据环境；过程图连接“准备怎样做”和“实际上做了什么”，不是预先限制 Agent 的完整剧本。

## 90 秒开题/答辩版

遥感领域已经提供了丰富的数据、算法和产品，但生态学家、规划人员和政策制定者仍要跨越数据发现、方法选择、软件操作和结果解释等专业门槛。URSA 因此从 data-centric 方法的局限出发，提出 user-centric remote sensing analysis：数据或产品供给不再被视为任务终点，而由用户先表达实际问题，再由智能系统组织数据、工具和分析结果。第一阶段的已发表工作回答“多智能体能否降低这一门槛”：Manager 澄清需求、Scientist 定义方法、Engineer/Executor 完成分析，并通过案例和 20 条任务的轻量评测证明可行性。

本章不是重新提出这个领域动机，而是追问其可靠性：用户要求能否被保持，工作流能否有效执行，失败反馈能否被正确处置，最终结果能否由过程证据核验。复盘发现，早期系统是否正确主要依赖提示词和聊天历史，错误往往到执行后才暴露，计划也缺少机器可检查的中间表示。

第二阶段先把 Engineer 的自由实现收束为 18 个标准工具，让调用、返回和错误可以测试。我们随后实现了带明确类型的静态工作流、规则检查、有限修补/停止和 ReAct 工具反馈循环，也探索过范围更广的运行时。相关研究表明，工作流图、ReAct、反思、过程追踪和检查点各自都有先例，因此第一章把增量收束为三个相互配合的对象：可调整的分层规划、随执行更新的过程图、基于检查点的局部恢复。

当前 v0.5.3 已把原先平行的 typed workflow 与真实模型链统一起来。Scientist 首次提交完整、无路径的计划图；runtime 验证依赖、类型、工具和交付义务；Engineer 只能执行当前 eligible 节点。工具失败后，Engineer 不能直接重试，必须由 Scientist 引用 observation、父计划和 checkpoint 对局部分支重新授权。系统再从 append-style trace 重建 observed graph，并检查报告是否由真实 artifact 支撑。最终 5×3 的 15 个槽全部达到 v2 evaluator closure，其中 task-11 的 B2/B3 完成局部重新授权和受限交付；该 diff 被诚实标为 `local_reauthorization_only`，不是规划优越性证据。

## 论文写作骨架

1. **领域出发点**：数据/产品供给丰富，但非遥感专业用户仍难以把实际问题转化为分析流程；
2. **范式基础**：已发表 URSA 将起点改为用户自然语言需求，ExpertsRS 提供角色和路由可行性；
3. **本章问题**：如何使这种用户需求驱动的工作流可靠形成和运行；
4. **失败分析**：需求可能遗漏、状态隐含、产出缺少明确类型、错误发现太晚、计划改写无法追溯；
5. **方法**：可调整的分层规划、随执行更新的过程图、基于检查点的局部恢复；
6. **系统支撑**：最小任务/工具/产出约定、18 个工具、ReAct 选择与执行分离、运行状态和记录；
7. **实验**：对话、静态规划、自适应规划和局部恢复的同任务对照，故障注入，任务与答案隔离；
8. **结果**：最终结果、执行过程和成本分别报告；
9. **局限**：可恢复故障范围、遥感语义覆盖、真实模型集成和外部有效性；
10. **与后续章节的关系**：第一章提供行动对象，第二章提供证据/科学约束，第三章评测长期可靠性与用户效用。

## 常见追问

**为什么不用 LangGraph 重写？**

框架迁移不能回答科学问题。当前优先冻结不依赖特定框架的任务、工具、过程图、错误和运行记录接口；只有当持久化执行成为实验需要时再选择具体运行框架。

**为什么需要多 Agent？**

角色分工来自已发表系统，用于隔离需求澄清、领域方法和工具执行；本章不把 Agent 数量优势作为新 claim，正式实验需要与单 Agent/自由规划在相同预算下比较。

**为什么不增加一个 Validation Agent？**

审核能力已经分层：Manager 管用户确认，Scientist/Engineer 对方法与实现负责，运行时用固定
规则检查工具约定、权限、预算和产出完整性，独立评测评价过程和结果。只有固定规则无法判断的
语义问题才触发没有执行权限的临时审核器。常驻审核 Agent 会增加同类模型错误、循环、成本和
决策权歧义，因此只保留为未来可对照的条件，不作为默认第四角色。

**repair 有多强？**

旧 `repair.py` 仍只处理“缺少一个输出且只有一个安全候选”的确定性基线。D2 另用真实工具失败触发计划修订，并从逻辑检查点复用元数据产出形成一条替代路径；这只证明最小机制可运行，不承诺通用搜索、撤销外部不可逆操作或自我学习。

**创新点会不会被 Spatial-Agent 覆盖？**

单纯的静态工作流图会被覆盖。候选差异是让过程图随真实执行更新，并让它服务计划修改和局部恢复；但 ReAct、DS-STAR、LATS 和过程追踪研究已经覆盖相邻思想，因此必须通过遥感故障边界和静态—自适应的同任务对照结果，才能支持本章贡献。

**当前完成到哪里？**

冻结 v0.5.3 已有统一 run/resume、真实模型结构化计划、plan-bound action、planned/observed graph、运行内 checkpoint 和独立 evaluator。历史摘要记载 121 项回归与 15/15 closure，但 5×3 原始包目前仍待恢复核验，不能报成 100% 任务成功率。2026-09-09 的 v0.5.4.dev0 开发分支完成 136 项回归及北京产品统计/地图/报告离线贯通；图件裁切经实际查看发现、修正并保留两次运行。下一步让知识依据参与领域任务决策，并建立通用 Agent 对照入口。第一章机制效应、第三章领域自主性与专题质量仍是不同验证责任。
