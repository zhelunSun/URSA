## 30 秒面试版

ExpertsRS 最初让非遥感专业用户用自然语言驱动 Manager、Scientist 和 Engineer 完成分析并获得可视化结果。升级没有放弃这条主线，而是增加三个机制：计划可以根据真实工具反馈调整；系统把原计划、真实动作、结果、失败和改道关系逐步整理成过程图；失败后从最近的安全检查点复用有效结果并尝试新路径。三个机制已在无 API、真实工具故障小样中形成最小闭环，下一步只需验证真实模型是否因此受益。

## 论文核心思想连续性版

原论文的 `Data–Tools–Brain` 没有被新运行时替代：Data 提供输入和真实工具反馈，Tools 从自由代码生成升级为受控工具，Brain 保留 Manager 澄清、Scientist 方法规划、Engineer 实现的自主分工。运行时只是三者共用的状态、执行边界和证据环境；过程图连接“准备怎样做”和“实际上做了什么”，不是预先限制 Agent 的完整剧本。

## 90 秒开题/答辩版

第一阶段的已发表工作回答“多智能体能否降低非专家使用遥感分析的门槛”：Manager 澄清需求、Scientist 定义方法、Engineer/Executor 完成分析，并通过案例和 20 条任务的轻量评测证明可行性。但复盘后发现，系统是否正确主要依赖提示词和聊天历史，错误往往到执行后才暴露，计划也缺少机器可检查的中间表示。

第二阶段先把 Engineer 的自由实现收束为 18 个标准工具，让调用、返回和错误可以测试。我们随后实现了带明确类型的静态工作流、规则检查、有限修补/停止和 ReAct 工具反馈循环，也探索过范围更广的运行时。相关研究表明，工作流图、ReAct、反思、过程追踪和检查点各自都有先例，因此第一章把增量收束为三个相互配合的对象：可调整的分层规划、随执行更新的过程图、基于检查点的局部恢复。

当前静态工作流和 ReAct 运行记录已分别闭合，独立审计也证明过程记录能够暴露波段和无效值语义错误。D2 进一步实现计划版本、过程图自动整理、逻辑检查点、18-tool 最小权限分类和一个真实工具故障分支：不存在的 `B99` 触发失败后，计划从已验证元数据检查点形成替代路径，并以 `B8/B4` 完成重试；目录外写入被拒绝。它仍是脚本化机制证据，下一步在 D3-light 比较静态预先规划、反馈后调整计划和检查点恢复。

## 论文写作骨架

1. **问题**：最终看似成功，不能暴露中间规划缺陷；遥感错误可能跨步骤静默传播；
2. **基线**：已发表 ExpertsRS 与当前 notebook 的角色和路由；
3. **失败分析**：状态隐含、产出缺少明确类型、错误发现太晚、计划改写无法追溯；
4. **方法**：可调整的分层规划、随执行更新的过程图、基于检查点的局部恢复；
5. **系统支撑**：最小任务/工具/产出约定、18 个工具、ReAct 选择与执行分离、运行状态和记录；
6. **实验**：对话、静态规划、自适应规划和局部恢复的同任务对照，故障注入，任务与答案隔离；
7. **结果**：最终结果、执行过程和成本分别报告；
8. **局限**：可恢复故障范围、遥感语义覆盖、真实模型集成和外部有效性；
9. **与后续章节的关系**：第一章提供行动对象，第二章提供证据/科学约束，第三章评测长期可靠性与用户效用。

## 常见追问

**为什么不用 LangGraph 重写？**

框架迁移不能回答科学问题。当前优先冻结不依赖特定框架的任务、工具、过程图、错误和运行记录接口；只有当持久化执行成为实验需要时再选择具体运行框架。

**为什么需要多 Agent？**

角色分工来自已发表系统，用于隔离需求澄清、领域方法和工具执行；本章不把 Agent 数量优势作为新 claim，正式实验需要与单 Agent/自由规划在相同预算下比较。

**为什么不增加一个 Validation Agent？**

审核能力已经分层：Manager 管用户确认，Scientist/Engineer 对方法与实现负责，运行时用固定
规则检查工具约定、权限、预算和产出完整性，独立评测评价过程和结果。只有固定规则无法判断的
语义问题才触发没有执行权限的临时审核器。常驻审核 Agent 会增加同类模型错误、循环、成本和
决策权歧义，因此只保留为未来可对照的条件，不作为默认第四角色。

**repair 有多强？**

旧 `repair.py` 仍只处理“缺少一个输出且只有一个安全候选”的确定性基线。D2 另用真实工具失败触发计划修订，并从逻辑检查点复用元数据产出形成一条替代路径；这只证明最小机制可运行，不承诺通用搜索、撤销外部不可逆操作或自我学习。

**创新点会不会被 Spatial-Agent 覆盖？**

单纯的静态工作流图会被覆盖。候选差异是让过程图随真实执行更新，并让它服务计划修改和局部恢复；但 ReAct、DS-STAR、LATS 和过程追踪研究已经覆盖相邻思想，因此必须通过遥感故障边界和静态—自适应的同任务对照结果，才能支持本章贡献。

**当前完成到哪里？**

静态工作流内核、科学前置条件与 ReAct 记录已分别闭合；D1 资产盘点完成，D2 的三个研究对象已在无 API、真实工具故障小样中统一贯通，43 项相关测试通过。源码已由第一章 baseline 提交固定，结果工件仍按入口重建；真实模型的静态—自适应 D3-light 对照尚未运行。
