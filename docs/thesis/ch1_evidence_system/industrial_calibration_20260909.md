## 判断

有必要按工业 Agent 的实际能力校准，但不应为了面试扩成通用平台。现有系统可以准确称为
“面向遥感任务、具有结构化执行控制和证据记录的研究型 Agent runtime”。
下一里程碑是：**让一项领域任务由模型结合专业依据完成，并能交给另一种 Agent 执行同一任务。**
这把既有 S2 知识协同和 S3 首个 live 小样连成一个可演示检查点；不跳过离线接入，也不提前启动大规模比较。

一个完整交付应能展示：公开需求及资源 → 获取专业依据 → 决定计算或解释边界 → 工具实际执行 →
引用产品和知识的回答 → 外部核验。还须有一个无法完成的情形，能明确澄清或停止并保存失败。
只在固定计划里增加一次知识查询，或在最终报告贴上知识段落，不算知识已参与求解。

## 工业参照意味着什么

以下是 2026-09-09 实际读取的官方文档，不是对框架在本项目中的实测。厂商写“production”不作为认证依据，
这里也不建立统一行业达标分数。代码库/SDK 与已经配置好、能接受任务的 Agent 系统须分开。

- OpenAI Agents SDK 文档列出工具循环、handoff、会话、trace、guardrail 和可恢复审批。
  这些说明执行支撑是常见基础设施；仅有角色、日志或 checkpoint 名称不能作为 URSA 的创新依据。
  [官方 Agents 文档](https://developers.openai.com/api/docs/guides/agents)
- LangGraph 区分线程 checkpointer 与跨线程 store，并明确内存保存器不能在进程重启后保留状态。
  因而需要检查持久化后端与实际恢复测试，不能把保存一份 JSON 与 durable execution 等同。
  [官方 Persistence 文档](https://docs.langchain.com/oss/python/langgraph/persistence)
- Claude Agent SDK 提供 Claude Code 的工具循环和上下文管理，以及权限、会话、MCP 和子 Agent。
  它可作为现成系统候选，但其模型/产品条件不能未经验证就视为与 URSA 可控对齐。
  [官方 SDK 概述](https://code.claude.com/docs/en/agent-sdk/overview)
- OpenHands SDK 提供自定义工具、代码执行、远程环境、上下文压缩等，主要面向软件工程。
  它是可考虑的代码型 Agent 候选；先验证能否读取遥感资源和同一工具，不把编码榜单成绩外推到遥感。
  [官方 SDK 概述](https://docs.openhands.dev/sdk/index)

我的判断是，URSA 的研究价值应落在遥感需求、产品依赖、科学依据、反馈与可核验交付的组织方式及效果上。
工业校准帮助发现真实缺口；是否有研究增量仍由章节实验决定。不要承诺通用系统一定更差。

## 下一里程碑的工作包

| 顺序 | 可评审交付 | 验收标准 |
| --- | --- | --- |
| 1：接入合同 | 一个知识问题的公开输入、资源/产品引用、答案/依据/适用条件、不可用状态；沿第二章真实入口映射 | 原始来源可定位；数值事实引用实际产品；不读评价答案；不把查表当独立推理证据 |
| 2：离线接入 | 同一 runtime 消费知识结果；至少记录一个决策采用/不采用某依据的原因 | 正常、知识不足、资源不兼容三个开发检查；保留首错；只说明协议贯通 |
| 3：领域 live 准入 | 对应 profile 的工具描述、资源视图、计划 schema、反馈与终态规则；小型接口探针方案 | 旧 NDVI 专用提示不误用；模型能生成合法计划/参数并处理一个错误；真实调用前固定模型与有界预算 |
| 4：首个完整领域小样 | 新 run 完成任务，知识/计算/报告引用闭合；另有明确不能完成的变体 | 同产品计数核验、解释的依据/适用性人工核验分开；记录所有失败和介入；不是统计效应验收 |
| 并行准备：比较接口 | 相同公开任务与资源许可、独立输出要求；一个通用 Agent 的无 API 接线方案 | 对照方无需提交 URSA 计划图/角色 JSON；能访问同等工具及知识；参考与评分目录不可见 |

当前批准范围可继续做 1、2 及比较接口准备；3、4 的模型配置、运行预算与正式研究输入尚未在本轮指定。
森林定义与格局参数沿作者已有口径核定，不用新增任意阈值制造工作量。本里程碑验收的是单任务系统小样，
不是新方法接受。比较设计详见 [对照准备](comparison_preparation_20260909.md)。

### 已核实的第二章接入点与首个实施动作

本轮低阶子智能体做只读定位，根智能体核查关键入口：

- 第二章 `scripts/ch2_pilot_run.py:episode` 驱动实际模型/工具循环；
  `scripts/ch2_pilot_environment.py:Environment` 提供真实栅格操作，明确只接受任务 `51/10`，
  当前围绕 NDVI/LST、场景选择、汇总和算术。Environment 本身不是完整知识求解服务。
- `scripts/ch2_pilot_contract.py` 有最终 `metrics/answer/limitations/unavailable` 协议；
  当前数值证据主要来自产品与 `summary:<n>`。知识记录来源与数值产品证据还需在服务合同中区分。
- `scripts/ce_context_builder.py` 的卡片投影不等于执行求解；
  `scripts/build_ch2_kvd_feasibility.py` 的 `UF-VAL-CLASS-01/UF-VAL-HAB-01` 是候选方向，
  不因存在 `SC2-03` 等编号就成为可直接采用的北京领域判据。本轮没有审核其科学充分性。

因此不能把北京分类摘要直接塞入现有 NDVI/LST 环境，也不能靠固定限制语句冒充知识推理。
首个实施动作应是从已能执行的第二章流程定义最小服务合同，并用原有开发 fixture 检查跨章传输：

| 方向 | 最小字段与约束 |
| --- | --- |
| 请求 | 专业问题、任务范围、逻辑资源/产品引用及 hash、允许的操作、剩余子预算；不含 evaluator 答案 |
| 返回 | 答案/方案、适用条件、未支持项、原始数值产品引用、知识来源引用、实际模型/工具用量、状态与失败原因 |
| 证据 | 来源证据和计算证据分开命名；保留第二章 run ID，并映射到可定位文件；不能只把文本贴到 Manager 报告 |
| 运行 | URSA 调用一次服务，但账本必须纳入服务内部所有模型/工具调用；不把嵌套 Agent 成本藏成一次工具调用 |

先证明接口能传递真实求解的输入、结果和失败，再核定北京问题所需的知识与专题操作。
原任务离线 fixture 只用于工程适配，不能当北京应用结果；现有知识覆盖不足时保留“尚未可接入”。
首个领域任务的选择应能让知识影响实际方法或解释；如果只重复已有固定 guardrail，就应换一个更合适的任务。

## 取舍

- **本阶段吸收**：真实知识接口、工具合同、结果引用、可比任务入口、失败归档；这些同时服务论文、演示与面试。
- **缩小后补齐**：若新任务需要重启恢复或自由代码执行，只实现其必需的持久化/隔离边界并做故障测试。
- **按需延期**：MCP 服务化、通用记忆、监控界面、异步队列。跨框架共享工具确有需要时再选择 MCP 等传输协议。
- **不纳入本阶段**：为面试重写成某框架、增加 Agent 数量、多租户平台、Kubernetes、云端大规模部署。

## 面试表达的更新原则

先讲真实用户问题和为什么普通工具调用不够，再讲 Agent 决策与确定性执行的分工，
接着用一条失败轨迹说明修复/停止/证据判断，最后区分方法实验、工程回归和领域结果。
可以展示研究型 runtime 的实物与取舍，不把项目包装成生产级平台。
历史 v053 的 15/15 是协议闭合且原始包仍待 laptop 恢复；当前北京链是离线工程证据，两个数字都不能当任务成功率。
本次同时校准了 [叙事卡](narrative_cards.md) 的当前入口；旧章节材料不替代现行分工。
