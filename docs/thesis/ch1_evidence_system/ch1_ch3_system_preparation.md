后续实施：下文“待实施”是接入前快照；已开展的开发与验收以 [阶段目标](domain_toolchain_stage.md) 为准。
依据：总控当前 `THESIS_STATE.md`、preflight 提纲 §4.2/4.4，以及本轮对 URSA 与北京参考工具的代码检查。

## 1. 概念上分开，代码保持可复用

第一章研究把需求变成可执行工作流的方法；第三章研究将该方法、第二章知识推理和领域能力组织成完整系统。
同一实现可以同时是第一章的实验载体、第三章任务运行模块的基础，但同一机制不能在两章重复作为新增贡献。

| 内容 | 第一章承担 | 第三章承担 |
| --- | --- | --- |
| 自然语言需求 | 对象、范围、目标、交付和必要澄清的表示及保持 | 将实际城市森林研究需求接到具体资源和产品 |
| 规划与反馈 | 任务依赖、计划调整、错误定位和局部恢复机制 | 复用经过验证的机制组织多个专题环节 |
| 运行支撑 | 说明实现方法所需的状态、工具执行和事实记录 | 说明模块协同、部署运行边界及跨产品连续交付 |
| 专业知识 | 方法实验中固定知识条件，避免混淆因果归属 | 接入第二章正常知识求解，支持方法选择、计算和解释 |
| 数据、样本、专题算法 | 用于方法验证的受控任务环境 | 资源组织、类别/时空语义、样本角色、算法接入和产品衔接 |
| 实验 | 同模型/工具/知识/数据条件下的方法比较与局部消融 | 真实领域任务的产品质量、任务完成、整合价值及代价 |

第三章可以引用第一章的计划与恢复机制，只需解释系统怎样调用和配置，不再完整推导算法。
第一章结果不能直接当作第三章完整系统的结果；第三章使用相同内核版本后获得的新任务证据单独归档。

## 2. 内容安排建议（沿现有提纲，不新增正式标题）

第一章内部顺序：需求解析与任务表达 → 计划组织及反馈更新 → 错误检查/局部恢复 → 方法实现与匹配实验。
URSA 的历史系统、角色和运行内核在这里作为方法基础简要交代；界面、数据目录和专题工具清单不占据方法主线。

第三章沿现有 §4.4 的三个部分展开：

1. **系统总体架构设计与构建**：保留任务运行、知识服务、数据与样本、分析工具四模块。
   从一个实际需求说明各模块交换什么，以及中间产品如何成为后续输入；运行内核属于任务运行模块的实现。
2. **领域数据与分析工具集成**：说明资源身份、类别/空间/时间语义、样本用途、工具输入输出和产品依赖。
   重点落实分类产品、森林对象、组成/格局结果的衔接，不只罗列已有算法名称。
3. **系统应用与效果验证**：准备真实任务和核定参考，开展同条件比较，报告产品质量、任务成功、
   结果一致性、科学解释、运行开销及必要人工介入。

四模块是责任划分；分类—森林提取—格局分析是产品依赖关系。两者不能混为同一层结构。
沿用作者删除冠层后的当前范围；早期 backend 中的冠层候选不恢复到本轮内容。

## 3. 系统应继续完善：以领域任务牵引

现有 v0.5.3 能支撑第一章的有界方法原型，尚不足以支撑第三章的完整系统构建。
继续开发的重点，是让各模块在真实任务中交换有效信息并交付连续产品。

| 准备项 | 本轮代码/资产事实 | 最小补齐方向 | 当前状态 |
| --- | --- | --- | --- |
| 多输入和资源语义 | `RunRequest.data_paths` 可列多个路径，但 `_accept_plan/_tool_arguments` 主要取第一个输入 | 以逻辑资源 ID 绑定分类栅格、AOI、样本/模型和知识来源；明确类别、CRS、年份与依赖 | 待实施 |
| 专题工具接入 | `TOOL_BINDINGS` 仅六项；参数 resolver 是按工具名分支，阈值固定 0.3 | 为获准领域操作提供有类型的参数解析、权限、输入输出验证；先接组成统计和同源地图 | 待实施 |
| 产品种类 | 模型决策的产物类型主要是 raster/index/mask/map/metadata/report/area_statistics | 扩展分类产品、类别组成表及后续结构产品的语义，保留历史 schema 行为 | 待设计兼容映射 |
| 知识服务 | 旧计划集中于 `ScientificConstraintPort`；没有因此形成知识求解接入 | 输入专业问题、观测/产品引用；返回答案或方案、依据、适用条件和计算引用；约束检查是其中一部分 | 待对齐第二章真实求解接口 |
| 参考工具与被测工具分离 | 北京脚本含计算函数，但 `main` 同时读取 intake、写 reference/图件 | 将确定性计算封装为可调用领域能力，参考评分另存，禁止把 reference.json 注入 solver | 待实施 |
| 样本/分类链 | 当前可直接用既有 2025 分类图；没有核实新分类推理的完整调用链 | 先固定样本、模型与特征身份，再补冻结模型推理入口；新训练是另一个工作包 | 待专项核查 |
| 长任务 | 当前为本地进程内执行；已有预算和运行事实 | 只有真实工具耗时需要时再补提交/查询/取消和去重，不先建分布式平台 | 按实测需要推进 |

`DecisionProvider` 已有 Protocol，后续不把它从零抽象作为新成果。
现在无需拆仓、重建调度器、增加常驻审核 Agent 或全面迁移 Harness 框架。
核心代码仍可留 URSA；领域实现放在哪里按现有所有权维护，复用通过明确接口完成，不要求立即搬代码。

## 4. 已完成的首条接入准备

选作工程接线起点的已有任务：描述北京 2025 分类产品在既定研究范围内的空间分布和有效像元组成。
这是第一条可运行产品链的起点，**单独完成它不足以构成第三章**。

本轮只读核查：

- 第三章 `task_card.json` 指定的分类栅格存在，SHA-256 与其 `fe89f606…ee369` 匹配。
- 栅格为 23,216 × 18,004、单波段、EPSG:4326、nodata=255；不把像元计数直接解释为真实面积。
- `BJuforebv4` 的 `.shp/.shx/.dbf/.prj` 均存在；完整 hash 复核见本轮资产回执。
- 第三章已存在确定性参考计算函数与图表；这不是 URSA 的执行结果。
- URSA 当前虚拟环境缺 `shapely` 与 `shapefile`（PyShp），所以尚不能直接运行该参考工具链。
  不向冻结 v0.5.3 环境临时补装依赖，后续用隔离的集成环境声明版本并检查兼容性。

具体 hash 与检查结果见 [资产回执](audits/20260909_ch1_ch3_asset_readiness.json)；
历史包的有限搜索与只读核验命令见 [恢复准备回执](audits/20260909_historical_run_search.md)。

候选首轮真实调用应完成：公开请求与资源引用 → 读取分类/AOI → 原网格组成计算 → 同源空间图 →

接入时只提供公开输入和交付要求，参考数值和评分条件留在系统外。

## 5. 从接线小样到第三章的充分内容

建议按依赖推进，而非用版本号承诺完成时间：

| 阶段 | 实物交付 | 完成后能够说明 |
| --- | --- | --- |
| 准备 | 历史包恢复清单；输入与环境回执；资源/工具/产物接口差距 | 后续运行可追溯、实施对象明确 |
| 一条完整产品链 | 相同入口完成北京产品组成与地图，报告引用真实产物，评价侧隔离 | 四模块接线的第一步成立；仍非第三章全部研究 |
| 领域系统主体 | 按已核定森林口径，接入森林提取与格局分析；第二章知识求解影响方法或解释 | 连续专题任务能协同求解，有明确领域系统实质 |
| 分类生成分支 | 样本/特征/冻结模型可调用并产生分类产品，与已有产品入口可选择 | 数据与样本模块、分类工具的作用得到实现；训练贡献仍依前期方法归属 |
| 应用验证 | 同任务/资源下的系统比较，核定参考与专题验证，记录交付、质量、一致性及人工介入 | 系统应用价值的证据；能归因时才解释整合机制增量 |

第三章可研究的实质问题是：不同数据/样本/方法的语义和产品依赖怎样在连续任务中正确衔接，
使专业研究需求获得完整且有依据的交付。整合本身不是自动成立的创新；需要对应设计选择和实际证据。
比较时固定第一章内核，尽可能使各系统具有相同数据、工具和模型，避免用“对方缺工具”制造优越性。
如果难以独立控制整合因素，就报告系统应用表现，避免强行宣称单一机制效应。
