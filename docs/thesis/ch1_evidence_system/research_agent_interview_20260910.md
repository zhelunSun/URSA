# URSA 研究型智能体：工程、算法与架构面试口径

2026-09-10。代码检查点 ead8a59，v0.5.4.dev0；正式工作副本为 D:/Projects/phd-thesis/URSA。
本文是当前代码与运行事实的项目说明，不接受新的科学贡献，也不替代第一章/第三章正式提纲。

## 判断

URSA 已具备有边界的遥感研究智能体运行时雏形：模型决策、计划提交、确定性准入、真实工具、观察反馈、状态和产物留存、报告核验都有代码与工程验证。可以把它作为一个系统项目深入讲解。

但“架构环节齐全”“当前领域任务稳定完成”“具有自主科研能力”是三个不同判断。前者已有实物，第二项尚未稳定，第三项尚缺知识与科学验证闭环。北京新领域链的离线两工具贯通和 G 的首轮真实交付，不能替代 URSA 自身端到端验收；两轮正常任务中 U 均停在澄清。本次反馈轮还暴露了结构化协议失败。

合适名称是“面向遥感分析、具有结构化执行控制和证据追踪的 research agent 系统雏形”。它已经包含超出聊天演示的运行支撑；当前强项是可检查、可追踪的有界执行，而非稳定自主解决任意遥感研究问题。

这些可以支撑 Agent 应用开发、后端运行控制、工具集成、可靠性与评测工程方面的项目追问。面试重点是具体失败如何经过上述边界，而不是报工具数量或框架名称。

本轮 154 项工程回归通过，30 个 Rasterio 既有同类弃用 warning；这说明测试覆盖的约束仍成立，不代表 154 个真实任务成功。本轮 G 在零工具调用下输出了虚构数字，首先被严格决策 schema 拒绝；本次未执行到产物核验层，不能把它讲成已实测语义审查识别了幻觉数字。产物层的拒绝能力另由工程测试支撑。

## 算法与研究方面可以讲什么

| 研究问题 | 已实现的机制 | 目前不能声称的效果 |
| --- | --- | --- |
| 如何把需求约束传递到执行 | 任务规格、交付义务和 typed workflow；计划接受及报告时检查义务保持 | 自然语言意图已经被完整理解；比单 agent 更准确 |
| 如何防止执行偏离计划 | 依赖/类型验证，依据节点状态求可执行集合，动作绑定已接受计划 | 新的通用规划算法或最优调度算法 |
| 如何根据失败反馈调整 | 计划版本、失败节点和下游范围检查，局部重新授权，planned/observed 过程区分 | 任意拓扑重规划；当前局部修订不允许增加/删除节点 |
| 如何避免无效重复计算 | NDVI 成功产物的运行内检查点、未受影响产物保留、受限后续执行 | 通用 durable recovery；已证明 checkpoint 独立降低成本 |
| 如何检验机制是否有用 | 第一章匹配条件与故障轨迹；第三章相同任务/资源/工具下的单 agent 对照入口 | 两轮开发六例具有统计代表性或构成多智能体优势 |

这是 Agent 算法工程与系统研究的内容。没有训练新基础模型，不能把调用 DeepSeek 说成自研模型；已有遥感工具的封装也不自动成为新的遥感算法。候选贡献应围绕需求保持、受约束计划—反馈—恢复及可核验交付的组合与效果展开，创新性和因果效应仍由文献与实验检验。

第一章拥有需求解析、规划和反馈/恢复方法；第二章拥有知识表示和推理；第三章拥有领域系统构建与应用验证。第三章复用同一 runtime，不为章节分工新建一套调度器。

## “五脏俱全”具体到哪一层

架构图继续使用 module_continuity_map.md 的三张唯一图源。该文中的能力端口和适配器设计表包含未来方向，不能把 SQLite、远程执行等候选项当作已接入。

| 层面 | 当前状态 | 对完整性的影响 |
| --- | --- | --- |
| 需求—规划—执行—反馈—交付 | legacy 小样与工程测试已贯通；北京 domain 使用相同调度器，但 live U 尚未完成正常任务 | 有完整执行骨架，领域决策稳定性仍欠缺 |
| 数据与专题工具 | 有绑定本地资源、元数据/遥感操作、北京分类统计和地图 | 尚无完整自动数据发现、样本管理及广泛专题任务覆盖 |
| 知识与研究依据 | knowledge_port.py 有带来源、适用性和子预算的请求/响应合同；当前 unavailable | 尚未接入真实知识服务，不能称知识驱动的方法选择或科学结论闭环 |
| 用户交互与状态 | run/resume、保存 provider 会话和文本澄清 | resume 只接受 answer，缺 AOI 后追加资源再继续尚未打通；不是崩溃恢复 |
| 运行可靠性 | 预算、应用层权限、hash、受限本地工具和逻辑检查点 | 同进程同步工具不可抢占；无已验证进程沙箱、通用幂等重放、掉电恢复 |
| 运维与协作 | 本地可复查输出、版本控制、测试与开发评测 | 尚未形成多用户服务、生产监控、长期记忆或自主跨任务科研工作空间 |

因此可以说“执行系统雏形已经比较完整，研究能力与长期运行能力正在补齐”。若把 research agent 定义为能独立查文献、选择方法、组织实验并验证新结论的系统，目前尚未达到该范围。

## 能直接用于面试的表达

我做的是面向遥感研究任务的智能体系统 URSA。核心问题是模型生成分析方案之后，怎样确保它遵守数据与方法约束、真实执行，并能在失败后保持用户目标。系统把模型的计划和工具执行分开，用有类型的工作流、节点依赖、资源权限和产物引用控制执行，记录计划版本、实际过程和失败；在已有 NDVI 链上实现了运行内局部恢复。最近我把同一运行时接到北京分类产品任务，并构建了同模型、同工具的单 agent 对照。真实开发验证也发现了多余澄清、非结构化响应和伪造完成，因此我把“约束能够拦截错误”与“Agent 能稳定完成任务”分别评价。接下来的重点是稳定领域决策协议、补齐输入后的继续执行，再接入有来源和适用条件的知识服务。

可准备的三段实物演示：一条已成功的 legacy 真实工具链；一条保存完整的失败—重新授权—检查点复用轨迹；一条本轮未完成案例及其拒绝位置。北京 G 首轮成功可展示工具与对照接线，但必须标注属于对照方，不能作为 URSA live 成功演示。

## 下一里程碑及取舍

下一步先做“领域协议稳定与可检查交付”：明确模型可见类别字典及资源语义；消除共同停止要求与 Manager 可选决策之间的接口歧义；用保留的非 JSON/虚构产物响应做离线拒绝测试，区分格式失败与依据不足。规则和任务冻结后，再单独指定新的有界 live 检查，保留当前两批，不继续在本轮刷提示。

正常交付稳定后，优先补“缺 AOI → 提交资源及 hash → 同一 run 继续”，这直接服务真实研究使用。知识接口保持现有合同，待第二章服务可用再验证它实际影响一次方法或解释决策。正式比较前另建保留任务和重复计划，不把当前开发题继续当泛化评测。

本阶段不为面试增加 Agent 数量、自由代码执行、复杂平台或云部署；只有真实研究任务需要时，再实现相应隔离与持久恢复。论文和面试共用可复查的项目事实，但工程完整性不能替代方法效果证据。
