# 2026-08-14 导师汇报简报：第一章从历史原型收敛为可实验方法基线

## 一句话结论

第一章已经不再是旧 notebook、独立 workflow 和评估 runner 的拼接：我把新增研究对象收敛到
一条统一输入输出链中，形成了可调整规划、执行过程记录和检查点局部恢复的**方法基线 v1**。
目前证据证明“机制能够运行并可被实验”，尚不证明“真实模型下效果已经提高”。

## 这项进展为什么是论文进展，而不只是工程进展

已发表 ExpertsRS 回答了“多智能体能否完成遥感分析”的初步可行性问题，也暴露了复杂请求中
规划和结果可靠性不足。大论文第一章新增回答的是：当真实数据、工具结果或失败与原计划不一致时，
系统如何有依据地调整后续计划、保存实际发生的过程，并从安全位置局部恢复。

本轮整合把三个论文方法对象落到了同一可观测实验载体上：

1. **可调整的分层规划**：计划有版本，真实 observation 可以触发有理由的修订；
2. **随执行更新的过程图**：原计划、实际动作、产物、失败和改道由运行事实重建；
3. **基于检查点的局部恢复**：复用已验证产物，只重做受影响部分。

因此，本轮的论文价值不是“增加了多少代码”，而是把第一章从冻结设计推进到
“可运行方法 + 可执行对照协议”的状态。

## 对“开题完成约 50%”的贡献判断

这里按“50%”而不是“5%”理解。50% 不能按代码量计算，需要：已有成果映射、新旧边界、三个研究
问题闭合、至少一个新增机制原型及匹配测试、第三项研究的最小任务—轨迹—评分闭环。

本轮对第一章开题门槛的推进是：

- 可版本化表示：已满足；
- 可运行 validator：已满足；
- 定向修复/正确停止：已满足；
- 已发表结果与新增贡献区分：已满足；
- 小型 matched pilot：离线预飞行已满足，真实模型结果仍未满足。

所以最稳妥的表述是：

> **论文已有工作量接近开题所需量级；第一章新增方法已经完成实现与实验准备，但“50%”仍需
> 第一章最小真实模型对照、第二章最小科学约束闭环和第三章最小评测闭环共同支撑。**

本轮显著降低了第一章“只是概念或系统拼盘”的风险，但不应人为换算为一个新的完成百分比。

## 明天建议采用的五页汇报结构

1. **问题来源**：已发表系统证明可行，但复杂任务中的计划正确性、结果正确性和失败恢复仍不足；
2. **新增方法**：只讲三个对象及其区别，不讲类名和框架名；
3. **方法载体**：一条 `输入 → 角色决策 → runtime 控制 → 真实工具 → observation → 修订/停止 → 报告`
   链；旧 notebook 是历史复现，新系统是新增方法的实验载体；
4. **初步证据与边界**：75 测试、离线真实工具场景、15 个条件槽预飞行；醒目标注“非 live 效果”；
5. **最小下一步**：三次 live smoke 后做 5×3 小对照，形成结果备忘即停止扩建，主投入回第二章。

## 90 秒演示方法

在仓库根目录运行：

```powershell
python -m ExpertsRS run `
  --request "Map NDVI for Dongcheng" `
  --data ExpertsRS/data/Sentinel2_Dongcheng_20230718.tif `
  --output-dir .test_tmp/advisor_demo
```

演示时只展示四样东西：用户请求、生成的 NDVI 地图、`result.json` 终态、`trace.jsonl` 中
“计划—工具—observation—artifact”的连续记录。然后用恢复测试说明失败分支：

```powershell
python -m unittest `
  ExpertsRS.test_system.UnifiedSystemTests.test_recovery_reuses_ndvi_checkpoint_without_recomputing -v
```

必须口头说明：当前 CLI 默认是 scripted offline 决策，真实 raster 工具和 runtime 是真的；这次
演示验证系统机制与证据链，不验证大模型推理效果。不要现场临时调用 API。

## 可说与不可说

可以说：

> 第一章新增方法已形成统一、可运行、可审计的离线基线，匹配实验协议已经能够通过同一入口预飞行。

不可说：

- 系统已经在真实模型下整体通过；
- 18 个工具都已能由 Agent 自主可靠选择和填参；
- 检查点支持任意崩溃后的通用恢复；
- 科学正确性或遥感精度已因多智能体方法提高；
- 多智能体普遍优于单智能体。
